# Plan 02-03: Score Display Contract Verification

<objective>
Add focused regression coverage and a lightweight smoke checklist so Phase 02 cannot silently regress back to key-driven, first-8-measure, single-SVG notation after the A4 renderer lands.
</objective>

## must_haves
- D-01: Full score preview must be protected by regression checks.
- D-02: Short built-in patterns must remain covered as sheet content.
- D-03: Internal display-mode behavior must be checkable without a user-facing mode switch.
- D-04: A4 page rendering must be validated by source/test contracts.
- D-05: Single-page centering must be covered by CSS/source checks.
- D-06: Multiple-page desktop grid behavior must be covered by CSS/source checks.
- D-07: Fixed-piano clearance must be covered by CSS/source checks and manual smoke.
- D-08: Loop control must be covered by source checks.
- D-09: Loop default-off behavior must be covered by source checks.
- D-10: Looping complete canonical source only must be verified manually after implementation.
- D-11: Key-change removal must be covered by source checks.
- D-12: Authored-key Fur Elise resolution must be covered by tests.
- D-13: Display-as-written direction must remain documented for future MusicXML work.
- D-14: Full score, no 8-measure cap, and no MusicXML/validation scope creep must be checked.

## truths
- D-01: Regression tests should guard sheet-first display.
- D-02: Regression tests should include a short built-in pattern.
- D-03: The test target is internal mode/default behavior, not a UI mode switch.
- D-04: A4 layout is verified through stable class/token checks.
- D-05: One-page centering is a CSS contract.
- D-06: Two-column desktop pages are a CSS contract.
- D-07: Piano clearance needs both source and browser smoke verification.
- D-08: Loop control is part of the playback contract.
- D-09: Loop starts unchecked.
- D-10: Complete-sequence looping is not practice range looping.
- D-11: Key selection stays removed from active UI.
- D-12: Fur Elise resolves in authored `Am`.
- D-13: Future MusicXML should plug into this score/display path as authored content.
- D-14: Validation and MusicXML import are still deferred after Phase 02.

<threat_model>
## Security Threat Model

**Scope:** Dev-only tests, source checks, and documentation updates.

**Threats considered:**
- Verification must not require a persistent server, backend, or new browser automation dependency.
- Tests that read source files can become brittle if they assert formatting rather than behavior-relevant contracts.
- Documentation must not imply MusicXML import or validation is complete in Phase 02.

**Mitigations required:**
- Use Node's existing built-in test runner.
- Assert stable identifiers/classes/functions, not arbitrary whitespace.
- Document manual smoke as verification for this phase, not as shipped user-facing UI copy.
</threat_model>
