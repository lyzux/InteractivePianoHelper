# Plan 02-02: A4 Full-Score Page Renderer

<objective>
Replace the capped single-SVG notation output with a sheet-first A4 page renderer that displays complete canonical score material, preserves event-ID highlighting across pages, and keeps long scores scrollable above the fixed piano.
</objective>

## must_haves
- D-01: Always prefer full score preview.
- D-02: Short built-in patterns must render on the same sheet surface.
- D-03: Display behavior must be explicit in code/metadata without preserving a prominent compact/full switch.
- D-04: Full score notation must be presented as A4-like pages.
- D-05: A single page must be centered.
- D-06: Two or more pages use two pages horizontally per row on desktop/wide layouts, with further rows below.
- D-07: The fixed piano keyboard must not obscure the page grid.
- D-12: Native-key pieces display in authored/original key.
- D-13: Future MusicXML files should be displayed as written.
- D-14: Remove the hard 8-measure cap, support full score rendering, and keep validation/MusicXML import out of scope.

## truths
- D-01: The score surface is the primary experience.
- D-02: Existing short pattern content is score content for Phase 02.
- D-03: Internal display metadata is enough for Phase 02 mode separation.
- D-04: A4 page proportion is the visual contract.
- D-05: One generated page centers horizontally.
- D-06: Multiple pages form a two-column desktop grid.
- D-07: The final page remains scrollable above the fixed piano.
- D-12: Key signatures come from authored sequence key, not visible key selection.
- D-13: Renderer architecture must not require content edits/transposition.
- D-14: Full score display replaces the current first-8-measures cutoff.

<threat_model>
## Security Threat Model

**Scope:** Browser DOM/SVG rendering of local canonical pattern data.

**Threats considered:**
- Renderer refactor must not introduce network calls, eval, user-upload parsing, or backend services.
- Large local scores can create many SVG elements; renderer should avoid runaway unbounded loops.
- Error messages must not render arbitrary external HTML because future import work is out of scope.

**Mitigations required:**
- Continue using local canonical sequences and VexFlow only.
- Keep pagination deterministic with finite page/system loops based on measure count.
- Use fixed user-facing error copy for renderer failures.
</threat_model>
