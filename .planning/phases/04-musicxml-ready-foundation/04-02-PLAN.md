# Plan 04-02: Browser Smoke Coverage

<objective>
Add a separate lightweight browser smoke check that serves the static app locally and verifies boot, pattern loading, notation SVG rendering, and play/stop highlight cleanup without making the normal unit test suite depend on browser automation.
</objective>

## must_haves
- D-11: Cover app boot, valid source loading, notation SVG/page render, Play/Stop, and highlight cleanup.
- D-12: Ask before adding or downloading browser automation tooling.
- D-13: Avoid full visual/SVG snapshots.
- D-16: Use recommended implementation defaults after any critical gate is approved.

## truths
- D-11: The real app behavior happens in the browser.
- D-12: Browser automation is the only known critical execution gate in Phase 04.
- D-13: Structural assertions are robust enough for smoke coverage.
- D-16: Execution should not pause for non-critical stylistic choices.

<threat_model>
## Security Threat Model

**Scope:** Local browser smoke test infrastructure and package scripts.

**Threats considered:**
- Browser automation may download binaries and add dev-only supply-chain surface.
- Static smoke server could accidentally bind broadly or serve outside the project root.
- Smoke tests could become flaky if they depend on exact SVG markup or audio timing.
- Autoplay/Web Audio behavior could cause tests to hang if assertions require audible playback.

**Mitigations required:**
- Ask before installing Playwright or equivalent browser tooling.
- Keep browser tooling as a dev-only dependency.
- Bind the test server to `127.0.0.1` and serve only the repository root.
- Keep `npm test` Node-only; add browser coverage under `npm run test:smoke`.
- Assert DOM/playback cleanup structure, not audio output or full SVG snapshots.
</threat_model>
