# Plan 04-01: MusicXML Adapter Contract And Documentation

<objective>
Create the implementation-facing MusicXML adapter contract that future parsing code will target, make the contract testable through a tiny pure module, and document how MusicXML data maps into the existing canonical score/event model without replacing current short pattern support.
</objective>

## must_haves
- D-01: Define an adapter contract, not a full importer.
- D-02: Target the existing canonical event sequence.
- D-03: Cover core MusicXML score structure and timing concepts.
- D-04: Document deferred/unsupported MusicXML concepts.
- D-05: Preserve page semantics in the contract.
- D-06: Represent MusicXML page layout and print hints.
- D-07: Keep VexFlow/A4 renderer as the active renderer for this phase.
- D-08: Keep current short patterns supported.
- D-09: Preserve source-scoped diagnostics and identity.
- D-10: Do not alter locked audio/keyboard/product behaviors.
- D-14: Document parser, validation, and future UI plug-in points.
- D-15: Ground mapping decisions in official MusicXML references.

## truths
- D-01: Phase 04 is an architecture foundation.
- D-02: Canonical events are the playback/notation source of truth.
- D-03: Future MusicXML parsing must handle measure cursors, not just arrays.
- D-04: Deferred support must be visible.
- D-05: Page fidelity is more important than arbitrary responsive reflow.
- D-06: Layout data belongs in the adapter result even before full renderer support.
- D-07: Renderer replacement would be a separate critical dependency/migration decision.
- D-08: `pattern` and `musicxml` are coexisting source types.
- D-09: Diagnostics must remain testable structured data.
- D-10: This plan is not a UI redesign.
- D-14: The next phase should know exactly where to plug in a parser.
- D-15: W3C MusicXML 4.0 docs drive the mapping.

<threat_model>
## Security Threat Model

**Scope:** Documentation, a pure adapter-contract module, and Node contract tests.

**Threats considered:**
- Future user-provided MusicXML is untrusted XML and must not become executable code.
- A future parser could accidentally bypass validation and register invalid canonical events.
- XML parsing can create browser safety issues if external resources or entity resolution are allowed.
- Adapter diagnostics could leak too much technical detail into user-facing UI if not separated.

**Mitigations required:**
- Contract docs must state that MusicXML is parsed as inert data only.
- Contract docs must forbid `eval`, `Function`, dynamic script import, and executable user content.
- Contract docs must require future MusicXML output to pass `validateResolvedSequence()` before registration.
- Contract docs must require source-scoped diagnostics with `sourceType: "musicxml"`.
- The module must remain pure: no DOM, network, audio, parser side effects, or renderer dependencies.
</threat_model>
