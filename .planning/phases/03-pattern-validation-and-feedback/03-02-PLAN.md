# Plan 03-02: Loader Validation Gate And Source Corrections

<objective>
Integrate the validator into pattern loading and registration so only verified sources become selectable, failed imports and validation failures produce structured developer diagnostics, and current built-in source data is corrected until all intended built-ins pass.
</objective>

## must_haves
- D-01: Enforce musical validation at the loader boundary.
- D-02: Run source and canonical validation before registration succeeds.
- D-03: Preserve structured diagnostics for rejected sources.
- D-04: Keep loader source records future-ready.
- D-05: Remove invalid patterns from selector options.
- D-07: Stop silently swallowing import failures.
- D-09: Correct built-in content instead of adding workarounds.
- D-10: Do not cement JS as the only future source.
- D-11: Keep valid short patterns supported.
- D-12: Fatal diagnostics block registration.
- D-16: Cover valid and malformed loader fixtures.
- D-17: Cover selector filtering and validation hooks.
- D-18: Preserve existing regressions.
- D-19: Assert codes and paths.
- D-20: Built-in defaults remain current product scope.
- D-21: Source-scoped records should support future imported entries.
- D-22: Do not implement future file picker/persistence.
- D-23: Implement folded validation hardening at load/registration.

## truths
- D-01: Valid selectable sources must be musically safe.
- D-02: Registration is the gate.
- D-03: Rejection details remain structured.
- D-04: `sourceType` is part of loader records.
- D-05: `getPatternOptions()` returns valid-only options.
- D-07: Import failures are visible to developers.
- D-09: Source corrections beat weak validator exceptions.
- D-10: MusicXML-backed real pieces are future scope.
- D-11: Short patterns survive through validation.
- D-12: Errors block; warnings do not.
- D-16: Malformed loader fixtures are required.
- D-17: Loader filtering is tested.
- D-18: Existing resolver/score tests remain green.
- D-19: Diagnostic codes/paths are testable.
- D-20: Default built-in library is current scope.
- D-21: Remembered import library is future scope.
- D-22: Multiple source types are prepared but not implemented.
- D-23: Required fields, notes/ranges, rests, timing, time signatures, native-key behavior, and cyclic assumptions are validated.

<threat_model>
## Security Threat Model

**Scope:** Runtime pattern imports, loader registry, rejected-source diagnostics, and built-in source corrections.

**Threats considered:**
- Silent import failures can hide broken modules and create misleading user state.
- Future imported MusicXML should not be treated like executable JavaScript.
- Detailed diagnostics could be exposed in UI if loader and notification concerns are mixed.

**Mitigations required:**
- Record import failures as rejected sources with `sourceType: 'pattern'`, source ID, and an error diagnostic.
- Keep user-facing notification copy separate from developer diagnostics.
- Do not add file picker, local persistence, or user-provided executable source support in this plan.
</threat_model>
