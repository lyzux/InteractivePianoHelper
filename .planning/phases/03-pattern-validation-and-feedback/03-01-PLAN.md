# Plan 03-01: Validator Core And Diagnostic Fixtures

<objective>
Create a pure validation module that verifies current pattern source objects and resolved canonical sequences with MusicXML-ready structured diagnostics, plus focused tests for malformed fixtures and existing musical regressions.
</objective>

## must_haves
- D-01: Validate MusicXML-ready musical components.
- D-02: Validate both source shape and resolved canonical sequences.
- D-03: Return structured diagnostics with source ID, source type, severity, code, path, and message.
- D-04: Keep validator source abstractions future-ready for MusicXML.
- D-09: Do not encode legacy exceptions for invalid current content.
- D-10: Do not cement executable JS as the permanent real-piece source.
- D-11: Short patterns must pass the stricter contract.
- D-12: Fatal errors block sources; warnings remain non-fatal only when safe.
- D-16: Cover valid and malformed fixtures.
- D-17: Cover all Phase 03 validation categories practical in pure tests.
- D-18: Preserve Lombard, Fuer Elise, chord, rest, transposition, timing, measure grouping, validation, and unsupported-key regressions.
- D-19: Assert diagnostic codes and paths.
- D-20: Leave future default library/import work unimplemented while keeping source typing flexible.
- D-21: Keep diagnostics source-scoped for future local-library imports.
- D-22: Avoid source-type assumptions that would block future MusicXML.
- D-23: Cover the folded validation todo slice.

## truths
- D-01: MusicXML readiness is a validator design constraint.
- D-02: Source and canonical validation are separate gates.
- D-03: Diagnostics are structured data, not just console strings.
- D-04: `sourceType` must be able to represent `pattern` now and `musicxml` later.
- D-09: Invalid current source must be fixed later, not accommodated by weak validation.
- D-10: Real-piece MusicXML migration remains a future direction.
- D-11: Existing short patterns remain only through strict validation.
- D-12: Severity controls whether a source can load.
- D-16: Malformed test fixtures are part of the plan.
- D-17: Broad validation coverage is required.
- D-18: Existing regression tests must keep passing.
- D-19: Codes and paths are stable enough for assertions.
- D-20: Default library behavior is future context only.
- D-21: Remembered imports are future context only.
- D-22: Future imported MusicXML is a source-type target, not Phase 03 scope.
- D-23: The validation slice of the hardening todo is in scope.

<threat_model>
## Security Threat Model

**Scope:** Pure validation code and unit-test fixtures.

**Threats considered:**
- Future user-imported MusicXML will be untrusted input, so diagnostics must not encourage executing source content.
- Current pattern files are executable local modules, but validation must not add dynamic evaluation beyond existing imports.
- Diagnostic paths/messages could leak implementation details into the visible UI if mixed with user-facing copy.

**Mitigations required:**
- Keep `js/patternValidator.js` pure and dependency-free.
- Treat validators as data inspectors; do not use `eval`, `Function`, remote fetch, or runtime code generation.
- Keep detailed diagnostics structured for console/tests; visible UI copy is handled in Plan 03-03.
</threat_model>
