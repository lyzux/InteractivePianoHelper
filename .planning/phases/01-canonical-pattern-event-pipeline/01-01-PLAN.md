# Plan 01-01: Canonical Resolver And Unit Test Foundation

<objective>
Create a pure canonical pattern resolver that adapts existing JavaScript pattern modules into explicit musical events, with unit tests covering the resolver's timing, loop-unit, transposition, rests/chords, native-key, and event identity behavior.
</objective>

## must_haves
- D-01: Canonical events must support syntactically valid notation rather than raw array visualization.
- D-04: Loop-unit behavior must be decidable per pattern through metadata/defaults.
- D-05: The model must be shaped as a professional future MusicXML adapter target.
- D-06: The model must avoid choices that prevent future whole-file MusicXML pattern loops.
- D-09: Unit tests must be introduced where useful.
- D-10: Test tooling must not break static browser usage.

## truths
- D-01: Visible notation must be syntactically valid music notation, not merely a visualization of arrays.
- D-04: Short-loop behavior must be decided per pattern through canonical metadata/defaults.
- D-05: Phase 1 must prepare seriously for future MusicXML integration.
- D-06: Future MusicXML-backed patterns may loop the complete imported file, so the model must not assume tiny JS arrays forever.
- D-09: Unit tests must be introduced around canonical event generation, timing, loop-unit decisions, transposition, rests/chords, and agreement.
- D-10: Minimal JavaScript test tooling is allowed only if static browser usage remains intact.

<threat_model>
## Security Threat Model

**Scope:** Pure resolver, pattern adapter, and dev-only unit test setup.

**Threats considered:**
- Executable pattern modules remain local repo-controlled; Phase 1 does not add user-uploaded executable code.
- Test tooling must not add a runtime server or backend surface.
- Future MusicXML/user-imported content is out of scope and must not be treated as executable JavaScript.

**Mitigations required:**
- Keep the resolver pure and dependency-free so future validation can inspect data before playback/rendering.
- Keep `package.json` scripts dev-only; the app must still load through `index.html` as static browser files.
- Do not introduce network-facing services or credential handling.
</threat_model>

<title>Create pure canonical resolver module</title>
<read_first>

<action>
Create `js/canonicalPatternResolver.js`. Export a resolver function named `resolvePatternSequence(pattern, options)` where `options` includes `patternId` and `key`. Also export reusable note helpers as needed, including a transposition helper that replaces the duplicated transposition logic currently present in `js/player.js` and `js/simplePatternLoader.js`.

The resolved object must include `patternId`, `patternName`, `selectedKey`, `nativeKey`, `isKeySupported`, `timeSignature`, `beatsPerMeasure`, `loopUnitBeats`, and `events`.

Each event in `events` must include `id`, `sourceIndex`, `startBeat`, `durationBeats`, `measureIndex`, `beatInMeasure`, and `hands`. `hands.left` and `hands.right`, when present, must each include `notes`, `isRest`, and `fingering`. Scalar notes must be normalized to one-item `notes` arrays. Chords must remain arrays. `null` notes must become rests.

Default loop-unit rules: if explicit pattern metadata such as `loopUnitBeats` or `loopMeasures` exists, honor it; otherwise expand short source cycles to the first complete measure; otherwise keep complete source material as the loop unit. For `patterns/lombardisch.js`, the default canonical loop unit must be one complete `4/4` measure with 8 events and `loopUnitBeats` equal to `4`.

For native-key patterns such as `patterns/furelise.js`, do not transpose. If the selected key is unsupported and the pattern returns no hand data, return `isKeySupported: false`, `events: []`, and a clear `unsupportedReason` string.
</action>
<verify>

- Search with `rg "_SHARP_P|_KEY_ST_P|_resolveNotesP" js/player.js js/simplePatternLoader.js` after Plan 01-02; these duplicated playback helpers should be gone by phase completion.
</verify>
<acceptance_criteria>

- Every event returned for Lombard has a unique `id`.

</acceptance_criteria>
